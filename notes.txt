Qwen3-VL encodes the camera frames inside Alpamayo: whether each image is encoded independently, and whether generate re-encodes images once per trajectory sample.
This confirms heavy redundancy: with 6 trajectory samples, the vision encoder processes 96 images per step, though only 4 are actually new (one per camera, since 3 of each camera's 4 frames repeat). Next I'll verify the encoder processes each image independently, which is key for exact per-image caching.

I built the visual feature cache as a separate module, visual_cache/, with unit tests, but it hasn't run on the real model yet. The GPU microbenchmark is the next step, and the closed-loop cache runs come after that.

The redundancy it targets: every inference sends 4 cameras × 4 frames to Qwen3-VL, and generate repeats those images once per trajectory sample (6). So the vision encoder runs on 96 images per step, and only 4 of them are new. Qwen3-VL encodes each image independently, so reusing an image's features is exact.

How it works:

Storage (cache.py): keeps each image's encoder output, keyed by a fingerprint of its pixels. The oldest entries are dropped first, and max_entries sets the size limit.

Skipping repeat work (encoder.py): replaces get_image_features on the loaded model. Only images that aren't cached go through the encoder, in one batch. The model's own code is unchanged.

Updating, two strategies:

exact: reuses only identical frames. Lossless.
near_duplicate: also reuses the closest previously encoded frame when the pixel difference is under a threshold. Each encoded frame can stand in for at most max_near_duplicate_uses others, so features still refresh in a static scene.
The near-duplicate tests caught a design flaw: the reuse limit didn't actually force a refresh. I fixed it by always comparing new frames against the frame that was actually encoded, so the error is bounded by the threshold.

Config: driver.model.visual_cache.*, off by default. Each inference's cache counts (images encoded and reused) go into latency.jsonl and the summary table.

Tests: 6 new unit tests use a stand-in encoder to check that cached output matches uncached output across a sliding window with repeated samples, that only missing images are encoded, plus eviction and the near-duplicate rules. All 110 fast driver tests pass, and lint is clean. With the cache off, nothing changes for the job you have queued, which is now estimated to start at 21:18.

The microbenchmark (visual_cache_microbench.py) loads the real Alpamayo 1.5 encoder. It reports encoder time with and without the cache, images encoded per step, and the largest difference between cached and uncached features. That difference should be only bf16 rounding noise, since GPU kernels can round slightly differently at different batch sizes. It uses random frames, which doesn't matter for exact reuse, so near-duplicate reuse is evaluated in the closed-loop runs.
